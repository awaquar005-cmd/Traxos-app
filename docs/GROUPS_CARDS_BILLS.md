# Groups, card statements and payment plans — 0.15.0 Personal

## Scope and boundaries

The owner explicitly chose **leave live sharing awaiting setup**. Groups here are fully local records, not online memberships. No invitations are sent, invitation acceptance is not simulated, no Supabase/Firebase group endpoint is called, and no current/shared-server balance is claimed. Live collaboration still requires a configured authenticated backend, membership authorization/RLS, idempotent command transport and server acceptance tests. The UI says Local only. Existing Google account/Drive backup setup is separate and unchanged.

### Groups

More → Groups supports creation/rename/archive/restore, local member creation/rename/archive, one fixed currency, expense payer and selected participants, equal/exact/percentage/share splits, dated history, partial net settlements and explicit reversals. Active members must belong to the same group; your own member cannot be archived; settle balances before archiving members/groups. Up to100 members and5000 original events per group; reversals retain their own rows and never erase the original. Latest100 history rows are displayed; all persisted events remain in backups. Group currency/self identity are stable. There is no contacts permission or automatic message sending.

Exact amounts must sum to the total; percentages use exact basis points and must total100; share weights are positive integers. Equal/weighted splits use largest remainder, with stable member-ID tie breaking, to conserve minor units deterministically. No currency Float/Double or cross-currency summing. Positive member net means receivable; negative means payable. Settlement is capped by both payer debt and recipient credit, including balance as of the settlement date. Reversing an earlier expense after settlement can legitimately produce a refund/overpayment balance; history explains the reversal.

**Personal reports vs cash:** each unreversed group expense contributes *your own share* to monthly/category spending, including where another person paid. Group records themselves do not alter account balances. If you already recorded the full payment in Activity, explicitly link that exact expense (amount/date/currency/self payer); its ordinary report contribution becomes0, while the group share supplies the personal expense. A linked reimbursement is excluded from income, and a linked outgoing group settlement is excluded from expenses because the personal share was already recognized. This handles mixed payers/net settlements without undercounting or double counting. Unlinked ordinary transactions retain their normal report treatment: link them to reconcile duplicates. Linked records cannot be edited/deleted until the group event is reversed/unlinked. Reversal preserves the actual transaction and restores its ordinary report treatment. Group records are local accrual-style spending, not synthetic bank transactions; receivables/payables are shown separately, not added to Home's bank balances.

### Advanced cards

More → Card statements (also Accounts overflow and Settings) reads existing credit-card accounts. Configure actual closing day1–31, due offset1–60 days after close, optional limit, manually specified default minimum due, default funding account and reminder offsets. Month-end uses the last available day. Limit/available-limit estimate is never an asset or Home balance. Cycle changes affect future estimates, not saved historical statements.

Enter the bank's statement amount/minimum/due date, or explicitly generate an **Estimated** outstanding snapshot from opening balance and recorded transactions up to closing. No bank scraping, bank-confirmed badge, interest formula or minimum-due percentage is invented. Bank-confirmed adjustments preserve the previous amount/minimum/due/estimated state and reason in statement revision history; they do not change financial transactions. A zero-paid statement can be voided and replaced while retaining history.

Consecutive statements can carry forward debt. **Historical snapshots overlap and must not be summed.** Each snapshot's remaining/minimum due subtracts actual non-deleted card payments after its closing date; an older statement's payment is therefore also reflected in a later snapshot when appropriate. Future-dated payments do not count as paid. Refunds after close may follow bank-specific due rules; use bank-confirmed adjustment rather than guessing. Current recorded card outstanding stays ledger-derived.

Pay uses the existing atomic paired bank-debit/card-credit writer and never adds an expense. Matching an existing card payment adds an auditable allocation reference without posting money. Allocations cannot exceed the payment or statement reference amount. Unmatch preserves the actual payment and therefore does not falsely reopen the due. Deleting/restoring the actual paired payment in Activity changes the due calculation reactively. Current recorded liability/source funds still limit new payments. A manual statement cannot create spendable money or silently adjust account balances.

### Subscriptions, bills and EMI

More → Subscriptions & bills supports manual plans, variable/fixed amounts, monthly/quarterly/yearly/weekly/daily/custom-day recurrence, a trial end, optional end date, funding account, category, reminder preference, pause/resume/cancel, actual payment history and latest-occurrence Undo. Inline account/category creation reuses the existing catalogue components. Optional details are collapsed. Quarterly/yearly/month-end/leap-day calculations preserve the original day anchor. Variable amounts remain blank until confirmed; no expected amount is presented as an actual charge.

A due date never posts an expense. Confirm an actual amount/date to create one expense, or match an unused existing expense with the same account/amount/date. Duplicate operation IDs and occurrence keys prevent repeated taps/retries. Future actual payments are rejected. Undo tombstones only an expense created by this plan; a previously matched record is kept. The historical occurrence remains marked undone and its due is restored. Only the latest unchanged occurrence can be undone. Historical funding/currency/EMI terms are protected once payment history exists.

**EMI:** select an already-booked card purchase and2–120 monthly installments. Principal amounts use exact integer division, with the remainder in the last installment. Recording an installment tracks already-booked principal without another expense or increase in card debt; only a manually confirmed actual fee creates a separate card expense. Paying the bank remains the usual paired card bill payment. This is a manual schedule, not a bank interest/amortization engine or an automatic EMI conversion; prepayment and bank term changes require explicit review/cancellation rather than invented calculations.

Detect examines only already-approved local ledger history (including transactions previously approved from SMS), requiring at least3 payments on distinct dates with monthly/quarterly/yearly cadence. Fixed versus variable amounts are suggestions; Review opens the normal editable form; Ignore persists a suppression. No raw SMS/image/network access or automatic plan/payment creation is added. Detection is a conservative heuristic, not a guarantee. Existing auto-posting Recurring rules are preserved separately: disable a legacy rule covering the same payment before using a confirmation-based plan, or match its actual entry rather than creating another.

### Offline reminders and Settings

Payment reminders have a global enable setting, default lead days for new plans/cycles, per-plan/cycle offsets, quiet hours and the existing real Android permission flow. WorkManager reconciles on app start, changes and periodically (6h). Notifications contain no merchant, amount, account number, CVV, PIN or gift secret; native lock-screen visibility is private. No exact-time guarantee is claimed under Android battery/OEM restrictions. Stable schedule/due/offset receipt tokens plus serialized reconciliation/OnlyAlertOnce prevent repeated delivery; paid/paused/cancelled/archived/changed schedules cancel stale visible notifications. Denied permission/channel access creates no delivered receipt. Trial reminders target the earlier trial end when it precedes billing. Quiet hours defer same-day delivery; a later overdue check uses the due-date token once.

## Persistence, backup and engineering

Room13 adds group/member/event/share/report-link tables, card cycles/statements/revisions/payment references, payment plans/occurrences, ignored suggestions and device-local reminder controls/receipts. Existing Room12 entities remain structurally unchanged; explicit12→13 SQL migration is exported and tested. No destructive fallback or signing change.

Financial metadata/history/linkages are included in the existing authenticated portable/Drive snapshots. Restore reads schema11/12 archives with empty new tables, validates table primary keys (including composite group shares), references, money bounds, split conservation, EMI terms/history and duplicate links, and aborts conflicting additive restores. Device-specific reminder receipts/settings and ignored suggestion preferences are excluded. Card vault/PIN/cloud sessions remain excluded. General ledger/group/plan metadata remain app-private SQLite plaintext; this is not a full-database encryption claim.

Group detail/editor and plan/history screens observe transactionally read Room relation snapshots, so members/events/shares and installments/status cannot arrive as inconsistent intermediate graphs. Repositories execute IO and atomic Room transactions; MoneyToolsViewModel owns single-flight writes, errors and completion across rotation. Normal editors are full-screen routed forms with saved draft fields, fixed Save, Back/discard confirmation and custom selection/dialog components. No new dependency, emulator, paid API or Play APK. Hero/logo/watermark, QR/barcode/images, gift wallet, IOUs, current account/card vault, recurring rules, voice/SMS approval, cloud/local recovery and all prior routes remain.

Validation used one Gradle worker, the existing1.5GB Gradle heap and one512MB test fork to limit memory. See PROGRESS.md and validation/money-modules for actual executed checks. Live group services are deliberately awaiting setup. Physical phone/OEM/notification/permission/IME/TalkBack/large-font/Google/backend acceptance remains distinct from host tests.
