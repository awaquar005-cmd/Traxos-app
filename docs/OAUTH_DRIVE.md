# Account linking, Drive OAuth and folder recovery — 0.13.0 Personal

## Actual configuration and acceptance boundary

The owner supplied an Android OAuth client for Google project `micro-atrium-514609-u5` and confirmed Drive API enablement plus package/SHA-1 registration. That permits the **Drive authorization** implementation; it does not supply a Firebase API key or the Web client ID required by Credential Manager sign-in. No Firebase Authentication configuration was supplied during development. Email/password and Google account-login code is implemented against Firebase's real REST endpoints, with a runtime public-configuration importer, but remains **unconfigured until the owner enables the providers and imports google-services.json**. It is not a simulated successful login or an email-only local account.

Host tests use isolated databases, JCE test keys and fake HTTPS responses. No live Google consent, account creation, real verification/reset email, Firebase token exchange, Drive upload to the owner's account, hardware Keystore or physical SAF provider result is claimed tested. The app must show success only after the respective real request succeeds. Shared-group sync/Supabase remain separate and unimplemented.

## Enable email/password and Google account sign-in

1. In Firebase Console, add/select the **existing Google Cloud project** `micro-atrium-514609-u5`. Do not create a separate project per expense group. Firestore, Storage, Analytics and shared-group infrastructure are unnecessary for this login slice.
2. Under Build → Authentication → Get started/Sign-in methods, enable **Email/Password** and **Google**. Configure the support email and keep the default one-account-per-email policy. Google-provider setup supplies a Web OAuth client; Credential Manager needs that client ID, not the Android client ID.
3. Add/register an Android app with package **app.traxos.finance**, current SHA-1 **42:E1:93:2C:DA:AB:EE:47:F4:B2:08:99:A0:A4:4B:BA:0A:92:E6:BE**. Add SHA-256 **9D:F8:F4:7A:6A:EF:A5:1F:5B:1B:61:DF:B1:A3:AE:A3:EA:15:97:57:E3:90:24:82:1A:0C:9F:FE:A4:99:0F:54** where offered.
4. Download the **public Android google-services.json** after enabling Google. Import it in Settings → Sync center / Account & Drive → Account setup → Import. The importer validates the package, extracts project ID/API key and a client_type3 Web ID, rejects private-key files, and does not execute URLs/instructions from the file. If Google/Web configuration is missing, Google account sign-in stays unavailable with setup guidance. The Android OAuth JSON already provided cannot substitute for this Firebase file. No private OAuth client secret, signing key, password or service-role key belongs in the app/chat/repository.
5. In Google Auth Platform, complete Branding/Audience and add the intended Google account as a test user while the OAuth app is in Testing. Keep Drive API enabled. Drive requests only **drive.file**, not unrestricted Drive access. API-key restrictions must permit Identity Toolkit/Secure Token calls from this package/signature; native requests include X-Android-Package and the current SHA-1 certificate headers. Do not configure a browser-referrer-only key for native calls. Extra App Check/CAPTCHA enforcement would need a separately supported integration; the app does not bypass it.

Firebase publicly identifies the project with an API key; real authentication still requires verified credentials/tokens. Configuration alone is not a connected session. No Firebase SDK/Analytics/Firestore dependency is added: requests use HTTPS to Identity Toolkit and Secure Token only. Credential Manager/googleid and Google AuthorizationClient handle their native trusted Google UI.

## Local user, sign-up, sign-in and one Google account

- Existing offline users keep all Room records, preferences, PIN, vault and navigation. The profile display name remains local. No forced online onboarding or automatic data replacement.
- Email sign-up creates a real Firebase user. Verify the email and refresh status before explicitly **Link**ing this phone. Email/password sign-in, verification requests, reset requests, recent-login password addition/change and encrypted session refresh are implemented. Password reset does not reset/bypass the offline app PIN.
- **Continue with Google** uses Credential Manager with a random nonce and the Web client ID. The nonce/account filter is checked locally; Firebase verifies the Google token's cryptographic signature/audience/issuer and returns the authoritative UID through accounts:signInWithIdp. A decoded JWT is never used alone as accepted authentication. No Web client secret is embedded.
- Email-first users sign in freshly, then continue with the **same verified Google email** to link the provider using the existing Firebase ID token. Google-first users can authenticate again and add a password to that same UID. Credential collisions are errors; accounts are not automatically merged by this application.
- Local users may authorize and link **Drive directly**, without Firebase/sign-up. Google Drive's actual `about.user.permissionId` and email establish the Drive owner after explicit consent and a Link confirmation. A Drive permission ID is not represented as a Firebase UID or Google ID-token subject. A later Firebase account must use the same email.
- The first confirmed Firebase UID/project and Drive owner are stored in an authenticated, device-bound file. Binding survives sign-out. A different UID, Google subject, email or Drive permission ID cannot replace it. Sign-out clears the local online session/Google credential-manager state, retaining records and ownership. Disconnect clears the current Drive access token/connection; it does not change ownership or delete Drive files. There is no unlink/rebind control in this release.
- Password sign-in to the same UID remains possible if its Google provider needs relinking; the original fixed Google subject is retained and only that subject can be linked again. Corrupt/lost binding keys fail closed for cloud binding; the app never silently regenerates an unbound identity around existing encrypted ownership files.

This is one local ledger linked to one account, **not** multi-profile switching. Switching authentication must never expose/merge a different person's ledger. Owner recovery uses the original provider/email recovery flow; no local reset bypass is added. Current Firebase project/API-key configuration is locked once bound; planned key rotation support is a later explicit migration rather than silently selecting another project.

## Local folder fix

The picker uses ACTION_OPEN_DOCUMENT_TREE with read/write/persistable/prefix requests and the **actual returned permission flags**. It checks provider capabilities using the Android26+ Bundle query API, persists the grant and creates/reads/deletes a non-financial probe before committing the selected folder. Read-only or unavailable providers report an actionable failure and do not overwrite the previous selection. Picker launch failure, cancellation and unavailable system Files/Documents app are handled. Android may forbid selecting a storage root: create/select a TRAXOS subfolder inside Documents/Downloads instead. Folder selection does not move the live Room database.

## Drive backup and restore

1. Settings → Sync center / Account & Drive → Authorize. Google consent is separate from account authentication. A returned token is checked against Drive's actual owner; first linkage requires confirmation. Subsequent attempts use/check the original owner. No financial record is uploaded by authorizing or signing in.
2. Create/select an app-created Drive backup folder. The narrow drive.file scope lists only app-accessible backup folders/files; this is not a browser of all unrelated Drive files.
3. Enter/confirm a12–128-character archive password. Choose whether to keep a local copy; enabled local copying requires a previously selected writable folder. Local mirroring and read-back finish before upload. Changing the local folder on retry creates/verifies a copy there too.
4. Create one immutable encrypted snapshot with the existing PortableBackup format and locally verify it. Reserve/persist a Drive-generated file ID. Store the resumable session URL and encrypted pending file privately, separate from financial rows. Upload fixed1MiB chunks, query server offsets on retry, reject stalled/invalid offsets and untrusted session hosts. Interrupted sessions survive repository/process restart; expired sessions restart with the same reserved file ID. Lost completion acknowledgment checks the existing file instead of creating a duplicate.
5. Verify server ID/size/checksum/owner, download the uploaded ciphertext again, compare its SHA-256 and authenticate/stage the portable archive. **Only then** persist a verified timestamp and clear the pending file. An upload acknowledgment alone is not success. Newer local changes are not automatically included. No financial records are overwritten or unsynchronized journal operations discarded.
6. List backups with pagination, choose one, enter its password, download/verify, review counts and explicitly Restore. The existing additive Room transaction adds missing rows, skips identical rows and aborts the entire merge on conflicting IDs/constraints. Tombstones, linked movements, gift histories/images and exact currency accounting remain. Expiry/recurring work is reconciled after restore. No automatic restore/sign-in upload.

Pending snapshots can be resumed or explicitly discarded; discard removes only the unfinished app-private encrypted copy, not ledger data or completed backups. A pending snapshot keeps its original Drive folder. No automatic/background cloud schedule or personal multi-device ledger synchronization is claimed. Network failures/consent denial/token expiry are visible; expired cached OAuth tokens are invalidated before reconnection.

Archive coverage/exclusions/limits remain in LOCAL_RECOVERY.md: **the entire card vault (PAN/CVV/expiry), offline PIN/biometrics, cloud sessions/ownership, pending Smart Add and device preferences are excluded**. Gift secrets/images are portable inside the password envelope and resealed with the destination Keystore key. General ledger storage remains app-private plaintext; this is not full-database encryption. Keep the password and a copy outside the phone; neither Traxos nor Google login recovers a lost archive password.

## Security, privacy and validation

Firebase ID/refresh tokens and binding/transfer metadata use a dedicated Android Keystore AES-GCM envelope plus AtomicFile, including interrupted-write backup recovery and write verification. Google access tokens/nonce/passwords remain transient, outside saved-state bundles/logs. No refresh token/client secret for Google Drive is stored by Traxos; Google Play services handles authorization renewal. All app HTTPS endpoints are fixed/allowlisted, use platform TLS, explicit timeouts, bounded reads and no redirect following. Financial contents are encrypted before leaving app storage; secrets never enter notifications/logs or plaintext CSV. Background previews remain governed by the existing release app lock; DEBUG screenshots remain enabled by user request.

INTERNET is new for these explicit online actions. No historical-SMS/storage/contact/camera permission is added. The existing bundled ML Kit barcode feature is retained. Its CCT diagnostic transport backend registration is removed now that internet is allowed; no OCR or analytics SDK is introduced. Google system/services may process operational diagnostics under their own policies; no blanket zero-vendor-telemetry guarantee is made. Actual network profiling/provider behavior remains device acceptance.

Versions were checked against official Maven metadata: credentials1.6.0, play-services-auth22.0.0, googleid1.1.1. googleid1.2.1 was rejected because its Kotlin2.4 metadata is incompatible with this project's Kotlin2.1.20; no unsafe metadata bypass/compiler upgrade was used. Single module, conservative Gradle, Personal APK only, no emulator.

Acceptance requires the owner's actual Google/Firebase configuration and physical phone: first/repeated/cancelled sign-in and Drive consent, wrong Google account, revoked grants/refresh, email verification/reset, Google↔password same UID, linked local-user upgrade, real folder grant after restart/revocation/low space, interrupted uploads/process kill, tampered remote files, cross-phone restore with different hardware keys and intact existing ledger. Host results are reported separately; they cannot certify real Google account/Drive access.
